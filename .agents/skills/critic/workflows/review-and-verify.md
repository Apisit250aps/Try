# Review and fix verification

Use for multi-note reviews, conflicting feedback and revisions. Ordinary short
critique can compress these steps. [Contract](../references/production-contract.md),
[rubric](../references/rubric.md), [P10/P15](../references/evidence-map.md).

## First review

1. Freeze the reviewed input inventory and brief/criteria versions. Record actual
   access, modalities, inspection coverage and reviewer relationship.
2. Read/watch/listen at the available scope before consulting others' verdicts
   when practical. Preserve strengths, audience information and first response.
   Missing capacity changes the scope; do not simulate sensory inspection.
3. Locate candidate issues; challenge each with intent, exceptions and counter-
   evidence. Merge repeated symptoms only when a shared cause is supported;
   retain links so a fix can be checked at every affected location.
4. Prioritize with consequence and confidence. Separate required fixes, disputed
   interpretations, optional alternatives and evidence requests. Return report
   and receiver-specific notes; no imaginary acceptance or silent maker edits.

## Contradictory notes

Record each note's author/role, input revision, location, evidence, desired effect,
suggested solution and constraints. Two prescriptions may seek the same effect
through incompatible methods, or evaluate different revisions/audiences.

- Resolve facts first: did the clue exist, was it visible, is that document current?
- Separate the concern from the prescription: “I did not infer the key transfer”
  does not mandate “add explanatory dialogue.”
- Find a compatible option under locks, or present distinct alternatives with
  benefits/costs. Do not average “shorten” and “lengthen” to an arbitrary middle.
- If creative priorities conflict, Director/user chooses. Preserve minority
  readings and Critic's independent recommendation with rationale. Specialists
  revise; a title or majority is not a substitute for evidence.

## Verification

For each returned revision:

1. Confirm actual new artifact ID/version, change authorization, superseded
   version, claimed fixes and stable-ID split/merge mappings if any.
2. Reopen the original expected/observed and acceptance criteria. Compare both
   versions at relevant scenes/regions/time ranges using appropriate modalities.
   A changelog, prompt or “fixed” comment alone is implemented-unverified.
3. Verify the **desired effect/constraint**, not literal compliance with a
   suggested solution. A different solution can pass. Record new evidence and
   remaining uncertainty. If insufficient, keep needs-evidence rather than close.
4. Inspect affected upstream/downstream dependencies: reveal order, earlier
   setups, later payoffs, episode knowledge, character/prop identity, boards,
   shot entry/exit, cut timing/audio and access materials as applicable. Check
   neighboring unchanged regions; a local repair can introduce a regression.
5. Mark verified or reopened with evidence, or disputed/declined with owner
   decision. List stale/uninspected dependent artifacts and owners. Technical
   verification, independent recommendation and creative approval are separate.

## Bound cycles and preserve independence

Use the agreed deadline/budget; if absent, propose **one focused revision and
one verification pass** for a small review (a local default, not a universal
production rule). Stop when criteria are met, the owner accepts/declines a
trade-off, critical evidence is missing, or the review budget is exhausted.
New material issues can be logged, but changing taste is not grounds for moving
the target. Report residual risks/deferred issues and the next decision instead
of looping or claiming completion. Additional cycles require actual task need.

When feasible/authorized, use fresh independent readings for high-impact disputed
claims, with the same artifact/brief and no first verdict. A same-reviewer second
pass is useful but not independent. Keep initial ratings and disagreements; do
not erase them through consensus. Separate test-author scoring from executor
output, and known-scenario retests from evidence on unseen work.
